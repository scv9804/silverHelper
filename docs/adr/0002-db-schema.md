# 0002. DB 스키마와 마이그레이션 방식

- 상태: 승인
- 날짜: 2026-10-13
- 관련: [`docs/specs/public-api.md`](../specs/public-api.md), `backend/src/main/resources/db/migration/V1__init.sql`

## 배경
- 혜택 데이터를 세 공공 API에서 수집한다: 복지로 중앙부처(`NATIONAL`), 복지로 지자체(`LOCAL`), 행안부 공공서비스(`GOV24`). 필드 구성, 변경 감지 방법, 하루 호출 한도가 서로 다르다.
- CLAUDE.md 파이프라인 원칙: 원문 해시가 바뀐 항목만 AI로 처리하고, Claude와 GPT 결과가 다르거나 검증에 실패하면 검토 대기열로 보낸다. 사용자에게 보이는 정보에는 출처 URL과 기준일이 있어야 한다.
- 장기요양 등급, 정확한 연령 하한, 소득 기준은 어느 API에도 구조화 필드가 없어 원문에서 AI로 추출해야 한다.
- 같은 사업이 복지로와 정부24에 중복으로 실려 있을 가능성이 높다 (public-api.md §4, 실호출 검증 전).
- Phase 1에서 세 작업자가 동시에 이 스키마를 쓴다. 테이블 구조는 여기서 확정하고 엔티티는 작업자가 만든다.

## 결정

### 1. 마이그레이션은 Flyway, Hibernate는 검증만
- 스키마 변경은 `db/migration/V{n}__설명.sql`로만 한다. 번호는 doyun이 배정한다.
- `spring.jpa.hibernate.ddl-auto=validate`를 모든 프로필에 적용한다(local 포함). 엔티티가 테이블과 다르면 앱이 뜨지 않는다.
- 이미 적용된 마이그레이션 파일은 고치지 않는다. 수정은 새 버전으로 한다.

### 2. 테이블

| 테이블 | 역할 | 주 담당 |
|---|---|---|
| `benefit_group` | 같은 사업을 묶는 그룹 (아래 §3) | jiho |
| `benefit` | 원천별 혜택 1건. 원천 키, 표시용 필드, 출처 URL, 기준일, 해시, 상태 | jiho 쓰기 / seojun 읽기 |
| `benefit_raw` | 원문 응답 보관 (해시가 다른 버전마다 1행) | jiho |
| `benefit_tag` | 생애주기·가구유형·관심주제 코드 | jiho 쓰기 / seojun 읽기 |
| `benefit_reference` | 문의처, 관련 사이트, 근거법령, 서식, 신청 절차 | jiho 쓰기 / seojun 읽기 |
| `ai_extraction` | Claude·GPT 추출 결과 원본 (JSON) | jiho |
| `benefit_eligibility` | 확정된 자격 조건 1행 (매칭에 쓰는 값) | jiho 쓰기 / seojun 읽기 |
| `benefit_group_candidate` | 그룹 병합 후보 | jiho |
| `review_item` | 검토 대기열 | jiho 쓰기 / 관리자 화면(Phase 2) |
| `collect_run` | 수집 실행 이력 | jiho |
| `api_daily_usage` | API별 일일 호출 수 (한도 관리) | jiho |

사용자·프로필 테이블은 넣지 않았다. 로그인이 Phase 2이고, Phase 1의 조건 매칭은 요청으로 받은 프로필로 계산한다. 필요해지면 V2로 추가한다.

### 3. 중복 사업 그룹 키: 대리 키 그룹 + 보수적 자동 병합
**결정**: `benefit_group`(대리 키 `id`)을 두고 `benefit.group_id`로 묶는다. 사용자 목록은 그룹당 1건만 보여주고, 상세에서 원천별 출처를 모두 보여준다.

- 수집 시 새 `benefit`은 자기만의 그룹을 하나 만든다(그룹 1개 = 혜택 1개로 시작).
- 병합 규칙
  1. **자동 병합**: 정규화한 서비스명(공백·가운뎃점·괄호 제거, 소문자)이 같고, 소관기관이 같거나 한쪽이 상위 부처이며, 지역(시도·시군구)이 같을 때만.
  2. **후보**: 이름 유사도가 높거나 AI가 같은 사업이라고 판단하면 `benefit_group_candidate`와 `review_item(GROUP_CANDIDATE)`를 만들고 사람이 확정한다.
  3. 병합은 그룹 이동이라 되돌릴 수 있다. 원천 행은 지우지 않는다.
- 대표 행 선택: `benefit_group.primary_benefit_id`. 기본 우선순위는 `NATIONAL` > `LOCAL` > `GOV24`(복지로 원문이 더 상세하고 출처 URL이 공식 복지 포털이라서). 대표가 종료·삭제되면 다음 순위로 바꾼다.

**버린 대안**
- *정규화한 서비스명을 자연 키로 사용*: 서비스명이 바뀌면 키가 바뀌고, 이름이 같은 다른 지자체 사업이 잘못 합쳐진다.
- *AI만으로 판단*: 비용이 들고, 잘못 합치면 사용자에게 엉뚱한 출처가 보인다. AI는 후보 제안까지만 한다.
- *원천 간 공식 매핑 ID 사용*: 세 API 사이에 공통 ID가 없다(P0-1b 실호출로 확인, public-api.md §10).

**근거 (P0-1b)**: 이름 완전 일치만으로 보면 A의 42%가 C와 겹치지만, B는 같은 이름의 다른 지역 사업이 363쌍이라 이름만으로 합치면 오병합이 생긴다.

### 4. 원천 키와 변경 감지
- `benefit`은 `(source, source_id)`가 유일하다. 복지로 두 API가 같은 `WLF…` ID를 쓰더라도 원천이 다르면 다른 행이다.
- `content_hash`(SHA-256 hex): 사용자에게 보이는 필드와 AI 입력 필드만 정규화해서 계산한다. 조회수(`inqNum`) 같은 값은 제외한다.
- `benefit_raw`는 `(benefit_id, kind, content_hash)`가 유일하다. 같은 내용을 다시 받으면 새 행을 만들지 않고 `last_seen_at`만 갱신한다.

### 5. 공개 여부와 기준일
- `benefit.verified_hash`: 마지막으로 AI 추출이 확정된(교차검증 통과 또는 사람이 승인) 원문의 해시.
  - `verified_hash IS NULL` → 아직 사용자에게 보여주지 않는다.
  - `content_hash <> verified_hash` → 원문이 바뀌었고 재검증 중이다. 이전에 확정한 조건으로 계속 보여주되 "정보 갱신 확인 중"을 표시한다.
- `benefit.status`는 원천에서의 상태다: `ACTIVE`, `ENDED`(시행 종료일이 지남), `REMOVED`(목록에서 사라짐). 사용자 노출 조건은 `status = 'ACTIVE' AND verified_hash IS NOT NULL`.
- 화면의 기준일: `last_collected_at`(우리가 마지막으로 확인한 시각). 보조 정보로 `base_year`(중앙부처 `crtrYr`), `source_modified_at`(지자체 `lastModYmd`, 정부24 `수정일시`)을 보여준다.

### 6. 자격 조건
- `benefit_eligibility`는 혜택당 1행이고, 확정된 `ai_extraction` 하나(`extraction_id`)에서 나온다. 매칭 API(seojun)는 이 테이블만 읽는다.
- **NULL은 "조건 없음 또는 원문에 언급 없음"**이다. 예: `min_age IS NULL`은 연령 제한이 없다는 뜻. `true`/`false`는 원문에 명시된 경우만 쓴다.
- 장기요양: `ltc_required`(등급이 있어야 함) + `ltc_grades`(허용 등급 배열, 1~5, 인지지원등급은 6).
- 값의 출처: `field_sources`(jsonb)에 필드별로 `STRUCTURED`(API 구조화 필드) 또는 `AI`를 적는다. 구조화 값과 AI 값이 다르면 확정하지 않고 `review_item(STRUCTURED_MISMATCH)`로 보낸다.
- 원천 코드(생애주기 `006` 등)는 `benefit_tag`에 따로 둔다. 1차 후보를 좁히는 데 쓰고, 최종 판정은 `benefit_eligibility`로 한다.

### 7. AI 결과와 검토 대기열
- `ai_extraction`은 원문 버전 × 모델 × 프롬프트 버전마다 1행이다(`UNIQUE(raw_id, provider, prompt_version)`). 같은 입력을 다시 돌리지 않게 해서 비용을 막는다.
- 결과는 `result`(jsonb)에 그대로 저장하고, `schema_valid`에 JSON 스키마 검증 결과를 남긴다.
- `review_item.reason`: `MODEL_MISMATCH`, `SCHEMA_INVALID`, `STRUCTURED_MISMATCH`, `GROUP_CANDIDATE`, `SOURCE_REMOVED`, `OTHER`. 대기 중(`PENDING`) 항목은 혜택·사유별로 하나만 둔다(부분 유일 인덱스).

### 8. 열거형과 ID
- 열거값은 PostgreSQL enum 대신 `varchar` + `CHECK` 제약을 쓴다. JPA `@Enumerated(EnumType.STRING)`와 바로 맞고, 값 추가는 제약만 바꾸면 된다.
- PK는 `bigint GENERATED BY DEFAULT AS IDENTITY`. 엔티티는 `GenerationType.IDENTITY`를 쓴다.
- 시각은 `timestamptz`, 날짜만 있는 원천 값은 `date`.

### 9. 이번에 하지 않는 것
- pgvector 임베딩 테이블: 챗봇(RAG, Phase 2) 때 V{n}으로 추가한다. 확장(`CREATE EXTENSION vector`)도 그때 만든다.
- 전문 검색 인덱스(pg_trgm 등): 혜택 수가 수천 건 규모라 당장은 필요 없다.

## 결과
- 테이블 소유 (Phase 1): `benefit`, `benefit_group`, `benefit_tag`, `benefit_reference`, `benefit_eligibility`의 JPA 엔티티는 `benefit.domain`(읽기용)에 두고, 파이프라인은 이 테이블을 JdbcTemplate으로 쓴다. 두 작업자가 같은 엔티티 클래스를 동시에 고치는 충돌을 막고, 대량 upsert는 JDBC가 단순하기 때문이다. 나머지 테이블은 `pipeline` 소유.
- 엔티티 작성자는 `V1__init.sql`의 컬럼 이름·타입에 정확히 맞춰야 한다(`validate`). 배열(`ltc_grades`)과 jsonb 컬럼은 Hibernate 7의 `@JdbcTypeCode(SqlTypes.ARRAY / SqlTypes.JSON)`로 매핑한다.
- 스키마 변경이 필요하면 작업자는 doyun에게 요청하고, doyun이 다음 버전 번호로 마이그레이션을 추가한다.
- 그룹 병합이 보수적이라 초기에는 중복 혜택이 목록에 보일 수 있다. 실호출 검증(P0-1b) 후 중복 정도를 보고 자동 병합 규칙을 조정한다.

## 변경 이력
- V2 (P0-4): `benefit`에 상세 화면용 원문 컬럼 `target_content`, `criteria_content`, `benefit_content`, `apply_content` 추가. 조회 API가 원천별 원문 JSON 구조를 몰라도 되게 수집 시 정규화해서 넣는다.
